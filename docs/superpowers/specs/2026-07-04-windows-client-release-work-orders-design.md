# Windows 客户端外发验收工单设计

## 目标

把当前 Token Eyes Windows/Tauri 客户端从“开发机可构建”推进到“可交给外部测试者安装验证”，并用贝叶斯验收表、硬门禁和独立对抗性终审约束结论，避免把局部测试或构建成功误报为可外发。

## 已确认基线

- Tauri 0.54.0 可以生成 EXE、MSI 和 NSIS 安装包。
- 当前 MSI 解包后只有 `token-eyes.exe`，没有 Node、CLI 或本地 API 运行资源。
- Tauri 启动代码仍要求系统 `node` 和源码仓库中的 `bin/tracker.js`。
- 当前工作区存在大量未提交/未跟踪内容，且有运行时文件未跟踪。
- `npm run ci:local`、`cargo fmt --check`、Dashboard/Rust 依赖安全审计仍有失败项。
- 当前 Windows 安装包未进行可信 Authenticode 签名。

## 工单边界

| 工单 | 单一职责 | 主要贝叶斯维度 |
|---|---|---|
| 01 | 建立可复现、可提交、门禁清晰的发布基线 | B1、B7 |
| 02 | 把 Node、CLI、本地 API 运行资源真正打入 Tauri 包并提供可见故障 | B2、B3、B7 |
| 03 | 清零高危依赖，接入可信签名和发布流水线硬门禁 | B4、B5、B7 |
| 04 | 合流 02/03，在无 Node、无源码的干净 Windows 环境做安装闭环 | B2、B3、B5、B6、B7 |
| 05 | 全新上下文独立复验全部证据并给出外发或打回结论 | B1-B7 |

## 串并行与上下文

```text
01（串行基线）
  ├─> 02（自包含运行时，独立上下文） ─┐
  └─> 03（安全/签名/CI，独立上下文） ─┤
                                      ├─> 04（合流后串行安装验收）
                                      └─> 05（全新独立终审上下文）
```

- 01 必须先完成，因为 02/03 需要稳定基线。
- 02 与 03 文件所有权分离后可并行；必须使用独立分支或 worktree，不能同时修改同一工作区。
- 04 必须读取 02/03 的提交并合流后执行，不能边合流边终验。
- 05 不能复用 01-04 的执行上下文。若 05 发现问题，退回对应工单修复；修复后重新创建全新 05 审查上下文。

## 验收原则

1. 任一 P0/P1 或硬门禁失败时，无论后验概率多高都不得外发。
2. 同一测试重复运行、同一构建日志的不同描述、执行者自述只能算一组相关证据。
3. 必须区分“受控 fixture”“本机真实日志”“干净机器安装”三类证据，不能互相冒充。
4. 真实签名证书、真实干净 Windows 环境缺失时必须标记 `BLOCKED`，不得使用自签名或开发机目录模拟通过。
5. 每份工单都先复现、再最小修复、再验证、再对抗性自审；05 再做独立终审。

## 自审结果

- 无未决标记或未定义占位要求。
- 工单职责无交叉开发；02/03 只在 04 合流。
- 结论范围限定为“可交给外部测试者安装验证”，不等同于正式生产发布。
- 签名证书和干净 Windows 机器属于真实外部前置条件，明确允许如实阻塞，不允许伪造证据。
