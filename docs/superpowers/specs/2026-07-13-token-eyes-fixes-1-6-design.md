## 4. 事项 1、2、7：桌面窗口可靠性与可见品牌

### 目标

Token Eyes 始终保持单实例；用户再次点击快捷方式时，已有主窗口必须从隐藏或最小化状态恢复、前置并获得焦点。所有 Token Eyes 用户可见表面统一显示 `Token Eyes`。

### 已实现设计

- 单实例插件在应用初始化最早阶段注册。
- 第二实例只向第一实例发送唤醒请求，随后退出，不创建第二个主窗口。
- 唤醒按固定顺序执行：取消最小化、显示窗口、设置标题、请求焦点。
- 原生端维护唯一显示名常量 `Token Eyes`，覆盖主窗口标题、托盘提示和运行时纠偏。
- 前端入口同步设置 `document.title = "Token Eyes"`。
- Tauri 产品名、窗口标题、安装器元数据和本项目生成的快捷方式名称保持一致。
- 只统一 Token Eyes 的用户可见表面，不触碰 CC Switch，也不为品牌统一重命名无用户影响的历史内部标识。

### 完成证据与剩余验收

- 仓库内单实例、窗口恢复、标题、路由和构建自动化验证已通过。
- 剩余人工验收：在真实安装环境连续点击快捷方式 20 次，确认仅一个进程/主窗口，并分别覆盖正常、最小化、隐藏三种状态。

## 5. 事项 3、4：Codex 官方账号授权状态机

### 目标

优先使用本机现有 Codex 官方登录直接查询额度；只有没有可用登录或刷新令牌失效时，才使用 OpenAI 官方 Codex app-server 在系统默认浏览器授权。授权成功不再被额度同步失败阻塞。

### 已实现设计

- 修复本机官方凭据发现默认目录错误；支持 `CODEX_HOME` 和系统主目录下的官方 `auth.json`。
- 官网检测先调用本机官方登录对应的用量接口，成功后清理遗留的等待授权状态，不弹出重复登录窗口。
- 本机登录缺失、过期且刷新失败时，才接入官方 `account/login/start` 等授权流程。
- 将 `authorization` 与 `quota_sync` 拆成两条独立状态链。
- 授权成功立即返回已连接状态；额度在后台独立同步，失败时允许原生重试。
- 不在前端、日志或普通配置中保存浏览器 Cookie、账号密码或明文 Bearer Token。
- Token Eyes 不再创建会滞留的自有登录窗口。系统浏览器标签页并非 Token Eyes 控制，是否自动关闭取决于浏览器与 OpenAI 官方成功页。

### 完成证据与剩余验收

- 协议、会话、超时、重复回调、失效账号和额度失败回归测试已通过。
- 本机只读实测已找到官方 `auth.json`，访问令牌、刷新令牌和账号 ID 均存在；真实官方用量请求成功返回周窗口已用 95%、剩余 5%，全程没有打开登录窗口。
- 剩余人工验收：用户覆盖安装后确认界面状态、取消授权可恢复、额度失败不影响连接成功。

- 不产生 Token，不进入 Token 趋势或 Token 排行。
- 汇率换算复用项目统一设置。
- 已覆盖 CRUD、汇率、月份边界、一次性花销日期和 UTC+8 跨日测试。

## 7. 事项 6：供应商 API 简化配置与真实财务能力

### 第一性原则

“能调用模型”“现金余额”“套餐 Token 额度”“月度/累计花销”是四种不同能力，不能互相冒充。不同供应商的财务 API 认证也不相同，因此界面应保持简单，但不能错误承诺所有平台只凭一个模型 API Key 就能查询现金余额。

### 供应商能力矩阵

| 供应商 | 真实目标 | 所需凭据/认证 | 当前状态 | 产品处理 |
|---|---|---|---|---|
| DeepSeek | API 账户余额 | 模型 API Key / Bearer | 已实现 | 解析官方余额；未公开的历史充值/花销明确显示不支持 |
| 阿里云（千问所属账号） | 阿里云账户可用余额 | Alibaba Cloud AccessKey 对签名 OpenAPI 请求 | 已实现 | 使用 BSS `QueryAccountBalance` 与 HMAC-SHA1；明确标注为阿里云账号总余额，AK Secret 仅存系统凭据库 |
| Kimi | Moonshot 账户可用余额 | Kimi API Key / Bearer | 已实现 | 接入官方 `/v1/users/me/balance`，读取 `data.available_balance` 并按 CNY 展示 |
| 火山引擎（豆包所属账号） | 火山引擎账户可用余额 | 火山引擎 AccessKey 对签名 OpenAPI 请求 | 已实现 | 使用 Billing `QueryBalanceAcct` 与 HMAC-SHA256；明确标注为火山引擎账号总余额 |
| MiniMax | 按量付费现金余额 | 官方公开 API 索引中没有余额接口 | 已核实为不支持自动查询 | 明示当前无公开余额 API，不抓取控制台 Cookie、不调用模型、不模拟成功 |

### 交互设计

- 用户先选择供应商，界面只显示该供应商必需的最少字段。
- DeepSeek、Kimi 显示 API Key；阿里云、火山引擎显示云账号 AccessKey ID/Secret，并解释这是财务 OpenAPI 所需凭据。
- 已知供应商由内置适配器补齐请求方法、签名、财务端点和响应解析器。
- 高级配置默认折叠，只为未知自定义财务接口保留。
- 每个供应商显示能力矩阵；不存在的能力显示“不支持自动查询”，不显示伪造的 `0`。
- 所有密钥只保存为系统凭据引用，API 和日志不回显明文；云厂商请求在原生端签名。

### 验收标准

- 每个已支持供应商有官方响应 fixture、签名/解析、401/403/429、超时、HTML 登录页和结构变化测试。
- 阿里云和火山引擎明确展示账户级口径；不会让用户误解为千问/豆包独占余额。
- MiniMax 在没有公开现金余额 API 时不会模拟成功、抓取 Cookie 或复用套餐额度冒充现金。
- 真实账号连接属于人工验收项；fixture 通过不等于真实连接成功。

### 完成证据与剩余验收

- 已为 Kimi、阿里云 BSS 和火山引擎 Billing 增加官方响应结构 fixture；DeepSeek 继续使用既有官方余额 fixture。
- 阿里云 RPC 签名通过官方公开 HMAC-SHA1 示例向量；火山引擎 HMAC-SHA256 使用固定时间和凭据的确定性回归测试。
- AccessKey ID/Secret 作为一个版本化凭据封装保存到现有系统安全凭据库；配置文件、前端 DOM、错误消息和日志均不回显两部分凭据。
- 界面按供应商只显示最少字段：DeepSeek/Kimi 为 API Key；阿里云/火山引擎为 AccessKey ID + Secret；MiniMax/智谱无公开现金余额能力时禁用保存且说明原因。
- 201 个相关 Node 测试、38 个相关 Vitest 测试、Dashboard 生产构建、copy 注册校验和 `git diff --check` 已通过。
- 剩余人工验收：用户在 Token Eyes 界面自行填入真实 Kimi API Key、阿里云 RAM AK/SK、火山引擎 AK/SK 后，与各官方控制台余额比对。凭据不得放入测试、文档或命令历史。

- 服务刷新后若过期，立即从当前列表消失并正确修正页码；仅耗尽不消失。

### 完成证据与剩余验收

## 9. 事项 9：本月总成本环比

### 统计口径

- 本月与上月都使用同一时区、币种和换算规则。
- 总成本口径统一包含：API 成本、Token 套餐/订阅摊销和“其他 AI 花销”。
- 正常公式：`(本月总成本 - 上月总成本) / 上月总成本 × 100%`。
- 上月为 0、本月大于 0 时显示“较上月新增 ¥X”，不显示无穷大百分比。
- 两个月均为 0 时显示“与上月持平”；减少时显示负向语义和对应颜色。

### 验收标准

- 覆盖增长、减少、持平、上月为 0、跨币种、月份边界和 UTC+8 跨日测试。
- 卡片显示值必须与成本明细聚合一致，筛选条件变化时不得拿全局值冒充筛选值。

### 完成证据与剩余验收

- 财务卡片改为浏览器时区下的当前自然月与上一自然月，不再把“近 30 天”或自定义 Token 日期范围误标为“本月”。

## 14. 事项 14：排行榜改为用户行内 Agent 使用分布

### 第一性原理

排行榜的核心问题是“谁用了多少、花了多少，以及这些用量来自哪些 Agent”。Agent 只是每个用户总量的组成，不应占据整张表的固定列，也不应让没有使用该 Agent 的用户背负大量 `0`。当前实现同时存在顶部 Agent 平铺筛选和 11 个固定 Agent 列，导致横向滚动、信息稀释和空值噪音。

### 设计

- 桌面排行榜默认只展示总榜，不再在顶部平铺 Codex、Claude、Hermes 等 Agent，也不显示“更多 Agent”选择器。
- 后端保留 `agent` 查询兼容能力，避免破坏旧链接和 Edge 接口；新客户端入口固定使用 `agent=all`。
- 每个用户行采用“排名 / 头像与名称 / Agent 使用分布 / 总 Token / 预估花销”结构。
- Agent 分布读取真实 `agent_metrics`；兼容旧快照时才回退到 `gpt_tokens`、`claude_tokens` 等旧字段。
- 只显示数值大于 0 的 Agent，按该用户的 Token 从高到低排列。每项显示真实 Agent 名称和格式化 Token；不显示未使用 Agent，不补零，不编造比例。
- 移除固定 Agent 表头、横向列拖拽、列顺序本地存储和横向滚动依赖；保留周期与“含缓存 / 不含缓存 / 预估费用”口径切换。
- 视觉遵循现有 Token Eyes 设计系统：冷静、数据优先、无装饰性渐变；1 米笔记本观看距离；单行优先、窄屏自然换行，不以缩小字号换取塞满。

### 验收标准

- 任意用户仅显示自己实际使用过的 Agent；测试覆盖 1 个、3 个、全部为 0 和旧快照回退。
- 榜单在 1200×800、1440×900 和 1920×1080 下无整表横向滚动。
- 顶部不存在 Agent 平铺按钮或“更多 Agent”；周期和统计口径仍可用。
- Agent 分布的合计与该行对应口径一致；缺失字段不能被当作 0 后继续显示。

## 15. 事项 15：排行榜三项全员汇总

### 第一性原理

“参与人数”“累计 Token”“累计花销”是三个独立事实，不能用随当前排序口径变化的 `total_score` 互相冒充。尤其切换到“预估费用”后，参与人数不应因为某些模型未定价而改变。

### 设计

- 排行榜标题下增加一条紧凑的三项汇总区：总参与人数、全员累计消耗 Token、全员累计预估花销。
- SQL/RPC 新增独立 `aggregate_total_cost_usd`，保留已有 `aggregate_total_tokens`；`total_score` 只负责当前排序口径，不再用作全员汇总文案。
- `participant_count` 按所选日期范围内 Token 大于 0 的独立用户计算，与含缓存/不含缓存/费用排序口径解耦。
- 分页使用独立 `ranked_entry_count`，避免“参与人数包含未定价用户，但费用榜分页数却按参与人数计算”的尾页空白问题。
- 花销明确标注为模型公开价估算，不表述为实际账单；汇率只影响展示，不修改 USD 原始累计值。

### 验收标准

- 三个值随日期范围变化，但切换含缓存/不含缓存/预估费用时，参与人数保持稳定。
- 全员累计 Token 等于同一快照内全部有效用户 `total_tokens` 之和；累计花销等于 `estimated_cost_usd` 之和。
- 测试覆盖未定价模型、零 Token 用户、空榜单、分页和 USD/CNY 展示。

## 17. 事项 17：Token 服务列表成功状态过滤与双层命名

### 第一性原理

### 验收标准

- 成功的 Xiaomi Standard、Codex Plus 可见；未配置 GLM Lite 不可见。
- 100% 耗尽但未过期仍可见；过期记录始终不可见。
- 同名套餐来自不同服务商时不会混淆；无内部 `xiaomi_mimo` 文本泄漏到主标题。

## 21. 事项 21：Windows EXE 秒级启动

### 已确认事实

- Rust 已将本地 Node 后端放到后台线程，前端也已有静态 `boot-splash`，因此不能再把“后端后台化”当成新的完成项。
- 当前生产构建初始 `main` JS 约 1,044,143 字节；`InsforgeAuthProvider` 同步引用 `@insforge/sdk`，使仅使用本地功能的桌面启动也承担云认证代码解析与初始化成本。
- 尚无“进程创建 → 主窗口可见 → 本地壳可交互”的可重复基准，所以当前只能标记部分完成，不能依据主观体感宣布秒开。

### 优化策略

1. 在仓库内新增 Windows 启动基准脚本，记录进程创建、主窗口句柄出现、前端首屏标记和可交互标记；至少 10 次冷/热启动，输出 P50/P95。
2. 保持本地后端异步，不允许概览、设置或排行榜资源预加载阻塞主窗口。
3. 将桌面本地启动不需要的云认证 SDK、登录弹窗、分析脚本和命令面板移出首包；OAuth 回调捕获仍保持同步，不能为了拆包再次破坏微信登录回调。
4. 首个 HTML 绘制只显示 Token Eyes 品牌壳和真实启动状态；React 接管后无白屏跳变。数据未就绪时显示局部骨架，不锁住侧栏和导航。
5. 对生产 EXE 重新测量；若剩余时间主要来自首次 WebView2/Defender 冷启动，报告可控代码耗时与系统外部耗时，不用延迟动画或常驻隐藏进程伪造“秒开”。

### 固定验收阈值

- 连续 10 次日常启动：进程创建到 Token Eyes 可见窗口 P95 ≤ 1 秒。
- 可见窗口到侧栏/返回入口可操作 P95 ≤ 500ms，总计 P95 ≤ 1.5 秒。
- 本地 API 和统计数据不得阻塞窗口；已有快照时，有意义数据 P95 ≤ 2 秒。
- 首次安装后的 WebView2/Defender极冷启动单独记录，不混入日常启动，也不能删除失败样本。
- 构建前后记录首包体积；首包未下降或启动 P95 未改善，不得把拆包工作标记为完成。

### 完成证据

- `@insforge/sdk` 改为动态导入；登录弹窗、命令面板、Analytics 和 Speed Insights 改为独立懒加载块；原生 OAuth 回调页面仍保持入口同步导入。
- 生产初始 `main` JS 由约 1,044.14kB 降至 691.53kB，减少约 33.8%；InsForge SDK 进入独立 163.13kB 块。
- 仓库内基准脚本仅启动并终止它创建的 `src-tauri/target/release/token-eyes.exe` PID。最终 10 次日常启动：可见 P50 57.3ms、P95 156.6ms；可见到系统响应 P95 19.2ms；总响应 P95 161.2ms，全部低于固定阈值。
- Dashboard 生产构建、Tauri release 和 NSIS 安装包构建通过。基准的“可操作”以 Windows 主窗口 `Responding` 为自动化判据；覆盖安装后的真实点击体验仍由用户人工验收。
