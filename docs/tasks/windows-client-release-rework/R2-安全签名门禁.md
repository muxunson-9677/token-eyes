# R2 - 安全、签名与发布门禁返工

## 目标

关闭旧 05 发现的 P1：dashboard/RustSec 高危漏洞、EXE/MSI/NSIS 未签名、workflow 上传前缺 fail-closed 门禁。最终必须做到生产依赖安全扫描通过，Windows 产物使用可信 Authenticode 签名，release workflow 任一门禁失败时不上传。

对应维度：B4、B5、B7。

## 第一性原理执行规则

1. audit 退出 1 就是不通过；不能用“可能不可达”替代修复或明确批准的例外。
2. 自签名不算外发证据。
3. 签名成功不等于可信；必须验证链、发布者、时间戳、摘要算法和 `Status=Valid`。
4. workflow 只有在失败时真正阻止 upload 才叫门禁。
5. secret 不能写入命令、日志、artifact、截图或工单。
6. 先记录旧失败，再最小升级和加门禁。
7. 不复制 R1 的 runtime bundler；只调用 R1 提供的 build/prepare 接口。

## 执行步骤

### 1. 保存失败基线

- [ ] 运行 root/dashboard production audit。
- [ ] 运行 `cargo audit`。
- [ ] 运行 `npm --prefix dashboard explain ws`。
- [ ] 运行 `cargo tree --manifest-path src-tauri/Cargo.toml --target x86_64-pc-windows-msvc --invert quick-xml`。
- [ ] 检查当前 EXE/MSI/NSIS Authenticode 状态。
- [ ] 检查 workflow 是否会在门禁失败时仍上传。

### 2. 最小依赖修复

- [ ] 升级 dashboard 直接/传递依赖，消除 production high。
- [ ] 升级 Rust 依赖或 Tauri 依赖链，消除 `quick-xml 0.39.4` high。
- [ ] 不使用 `npm audit fix --force` 进行无边界升级。
- [ ] RustSec warnings 逐项分类：Windows 可达、构建期、非 Windows、等待上游；high 不允许永久 ignore。

### 3. 签名流程

- [ ] 明确正式证书来源、发布者主体、有效期、时间戳服务、CI secret 名称；不得记录 secret 值。
- [ ] 打包前签主 `token-eyes.exe`，确保安装包内嵌 EXE 已签名。
- [ ] 生成后分别签 MSI 和 NSIS。
- [ ] 使用 SHA-256 摘要和可信时间戳。
- [ ] 签名后计算 SHA256SUMS。
- [ ] 上传前验证三个产物 `Status=Valid`，发布者主体符合预期。
- [ ] 缺正式证书时，本工单可完成代码/门禁，但执行状态必须 `BLOCKED`，B5 不得达标。

### 4. workflow fail-closed

- [ ] upload 前运行 `npm run ci:local`、dashboard test/typecheck/lint、root/dashboard production audit、Rust fmt/test、cargo audit。
- [ ] 调用 R1 的 runtime prepare/build。
- [ ] upload 前解包或检查 MSI/NSIS，验证 runtime manifest、node、tracker、dashboard、license。
- [ ] upload 前验证签名 Valid 和 SHA256SUMS。
- [ ] workflow tests 覆盖 audit 失败、runtime 缺文件、版本漂移、签名无效、旧包 glob 混入。
- [ ] release-dmg 保持 draft，Windows/macOS 任一失败不能提前公开。

## 签名验证命令

```powershell
$ReleaseRoot = (Resolve-Path "src-tauri\target\release").Path
$Artifacts = @(
  (Join-Path $ReleaseRoot "token-eyes.exe"),
  (Get-ChildItem (Join-Path $ReleaseRoot "bundle\msi\*.msi") | Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName,
  (Get-ChildItem (Join-Path $ReleaseRoot "bundle\nsis\*-setup.exe") | Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName
)
$Artifacts | ForEach-Object {
  Get-AuthenticodeSignature $_ | Format-List Status,StatusMessage,SignerCertificate,TimeStamperCertificate
  Get-FileHash $_ -Algorithm SHA256
}
if ($Artifacts.Where({ (Get-AuthenticodeSignature $_).Status -ne 'Valid' }).Count -gt 0) {
  throw "One or more Windows artifacts are not validly signed"
}
```

## 对抗性审查要求

至少三轮：

1. 正常路径：audit、cargo audit、签名、workflow tests 全部通过。
2. 负向路径：制造 audit 失败、runtime 缺文件、签名无效、版本漂移、旧 0.1.0 artifact 并列，确认 upload 不执行。
3. secret/artifact 路径：扫描 workflow 日志、artifact 清单、源码、dashboard dist 和解包目录，确认无 PFX、密码、API Key、`.env`。

发现问题必须记录、修复、重跑受影响轮次。最后一轮无新 P0/P1 才能结束。

## 验收标准

- root production audit 无 high/critical。
- dashboard production audit 无 moderate/high/critical，除非有用户批准且非 high 的限期例外。
- cargo audit 无 vulnerability。
- EXE/MSI/NSIS 三个产物 `Status=Valid`，发布者和时间戳正确。
- workflow 在测试、安全、runtime、版本、签名任一失败时不上传。
- SHA256SUMS 在签名后生成。
- B4/B5/B7 计算阶段后验；最终阈值由 R5 判定。
