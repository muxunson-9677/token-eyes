# R3 - 合流、最终构建与干净 Windows 安装验收

## 目标

把 R1 自包含运行时和 R2 安全/签名/门禁合流到唯一 HEAD，生成唯一推荐 Windows 外发安装包，并在无 Node、无源码、无旧服务的干净 Windows 环境完成安装、首次启动、本地 API、连续同步两次、故障恢复、重启、重装、卸载验证。

对应维度：B1、B2、B3、B5、B6、B7。

## 第一性原理执行规则

1. 测试对象只能是最终签名安装包，不是开发机 EXE。
2. 干净环境必须证明无 Node、无源码仓库、无旧 Token Tracker/Token Eyes 服务。
3. 窗口打开不等于可用；必须验证进程来源、本地 API、数据读写和错误恢复。
4. 任一二进制改变后必须重新签名、重新哈希、重新解包、重新安装。
5. 不能手工补文件后宣称安装包自包含。
6. 不读取或记录真实消息正文、提示词、API Key、Cookie。
7. 发现架构性问题退回 R1/R2；只做最小合流修复。

- [ ] 输出唯一推荐安装包；禁止同时推荐旧 0.1.0 或未签名包。

### 4. 干净 Windows 环境基线

- [ ] 记录 Windows 版本、架构、WebView2 版本、用户权限、VM 快照 ID。
- [ ] 证明 `node --version` 不可用或 Node 不在 PATH。
- [ ] 证明无源码目录、无 `bin/tracker.js`、无旧安装和 7680/附近旧服务。
- [ ] 保存安装前进程、端口、安装目录基线。

### 5. 安装与首次启动

- [ ] 校验安装包 SHA256 与 R3 输出一致。
- [ ] 验证 Authenticode `Valid`、发布者正确、没有未知发布者警告。
- [ ] 使用标准非管理员用户安装推荐包。
- [ ] 验证窗口进入本地 Token Eyes 页面。
- [ ] 验证本地 API 子进程来自安装目录内 bundled `node.exe`。
- [ ] 验证 `/api/local-auth`、协议版本、capabilities 和三个核心只读端点。

### 6. 数据与同步

- [ ] 使用受控 fixture 验证至少两个 Agent 的目录检测、保存和同步。
- [ ] 同一输入连续同步两次，第二次不得重复累计。
- [ ] 使用至少一个真实受支持 Agent 本地日志验证计数；只记录计数和脱敏路径。
- [ ] 修改设置，重启后验证持久化。

### 7. 生命周期与故障恢复

- [ ] 关闭再启动；无孤儿后端。
- [ ] 连续启动两个客户端实例；无数据损坏或无限拉起后端。
- [ ] 占用端口、断网、后端崩溃、runtime 文件损坏；验证可见错误、脱敏日志和重试恢复。
- [ ] 相同版本重装或修复安装；用户数据不丢。
- [ ] 卸载后进程、安装目录和快捷方式清除；默认保留用户统计数据。
- [ ] 重装后能读取保留数据，或按明确迁移策略处理。

## 对抗性审查要求

至少四轮：

1. 自动化门禁复核。
2. 正常用户安装路径。
3. 故障和破坏路径：无 Node、端口占用、断网、runtime 损坏、后端崩溃、重复启动。
4. 重装/卸载/保留数据路径。

任一轮失败：追加记录、最小修复、重新构建、重新签名、重新哈希、重新解包、从受影响路径重跑。

## 验收标准

- 唯一 HEAD 通过全部自动化、安全和 workflow 门禁。
- 唯一推荐安装包签名 Valid、发布者正确、SHA256 已记录。
- 解包包含完整 runtime。
- 干净 Windows 无 Node/无源码仍完成安装、本地 API、同步两次、故障恢复。
- 重启、重复启动、断网、后端崩溃、重装、卸载均有新鲜证据。
- 没有未关闭 P0/P1。
- 输出 B1/B2/B3/B5/B6/B7 阶段后验；最终阈值由 R5 判定。
