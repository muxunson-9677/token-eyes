# R4 - 完成前总复审与返工收口

## 目标

在 R5 独立终审前，由主线集成上下文主动复打一遍旧 05 的所有失败点和 R1-R3 的完成证据。R4 是完成前强审查，不是最终独立签发；可做最小集成修复，但发现 R1/R2 架构性问题必须退回对应工单。

对应维度：B1-B7。

## 第一性原理执行规则

1. 默认 R3 仍可能漏证，必须主动找反例。
2. 不采信“R1/R2/R3 已通过”的结论；必须读代码、读 workflow、跑命令、查产物。
3. 同一证据只算一次，旧截图旧日志不能替代本轮复验。
4. 发现任何 P0/P1，先追加记录，再修复或退回。
5. 任一二进制变化后，重新签名、哈希、解包、安装。
6. R4 可以修最小合流问题，但不能最终签发。
7. R4 结束后必须给 R5 提供证据索引，而不是长篇口头总结。

## 执行步骤

### 1. 证据完整性审计

- [ ] 检查 R1/R2/R3 是否都有开始记录、失败基线、修复动作、必跑命令、对抗性审查轮次、B 维度计算。
- [ ] 检查最终安装包路径、版本、发布者、SHA256、签名时间戳、解包目录、干净 Windows 证据是否齐全。
- [ ] 缺任一项，写 `BLOCKED` 或退回对应工单。

### 2. 旧 05 失败点逐项复打

- [ ] 搜索 Release 主路径是否仍有 `Command::new("node")` 或向上找源码。
- [ ] 检查 `tauri.conf.json` 和解包目录是否包含 runtime resources。
- [ ] 复跑 dashboard audit、cargo audit、反向依赖链。
- [ ] 复查 EXE/MSI/NSIS `Status=Valid`。
- [ ] 复查 workflow upload 前的 fail-closed gate。
- [ ] 验证无第二干净 Windows 缺证。

### 3. 受控负向探针

- [ ] 删除 runtime 关键文件副本，workflow/本地校验必须失败。
- [ ] 篡改已签名 artifact 副本，签名校验必须失败。
- [ ] 构建目录同时存在旧版本和当前版本，upload glob 不得匹配旧版本。
- [ ] 制造版本不一致，workflow tests 必须失败。
- [ ] 制造 audit failure fixture，upload 不得执行。

### 4. 最后主线安装抽查

- [ ] 使用与 R3 不同的干净快照或恢复后的新快照抽查安装。
- [ ] 验证首次启动、本地 API、同步两次、重启、卸载核心路径。
- [ ] 如果没有第二环境，R4 必须 `BLOCKED`，不得把 R3 环境复用为独立证据。

## 对抗性审查要求

至少五轮：

1. 证据文件完整性审查。
2. 自动化/安全/签名复跑。
3. workflow fail-closed 负向审查。
4. 产物篡改/旧版本误传负向审查。
5. 第二干净 Windows 安装抽查。

发现问题必须记录并修复；修复后从受影响轮次重跑。无法修复或缺环境时输出 `BLOCKED`。

## 验收标准

- R1-R3 证据完整且没有矛盾。
- 旧 05 的 P0/P1 全部关闭。
- 最终包可被 R5 重新独立验证。
- 有明确 R5 证据索引：HEAD、installer path、SHA256SUMS、signer subject、clean Windows snapshot IDs、logs/screenshots paths、workflow negative test outputs。
- B1-B7 阶段后验全部达到进入 R5 的前置要求；最终外发结论仍由 R5 给出。
