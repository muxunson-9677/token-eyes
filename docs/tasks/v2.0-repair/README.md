# Token Eyes 2.0 修复工单入口

## 中文简述
这组工单不是新增 2.0 功能，而是修复 01/02/03/04 已执行结果中没有达到验收标准的部分。依据来自本轮贝叶斯验收：构建和部分测试通过，但真实项目路径前端、API 计费接入、请求日志页码跳转、飞书 2.0 读回证据仍不足，因此不能做完整验收。

## 贝叶斯验收结论
- 假设：`H = 2.0 四个工单已按需求完整高质量完成`
- 后验估计：`P(H|E) ≈ 8.2%`
- 结论：不能放行，需要先执行本目录修复工单。

## 工单目录
- `01-project-path.md`：真实项目路径用量修复。
- `02-request-log.md`：请求日志 10 条分页与 CC Switch 页码跳转修复。
- `03-cost-billing.md`：API 计费接入、成本累积与支出页测试修复。
- `04-qa-feishu.md`：飞书 2.0 同步读回与最终对抗性验收。

## 执行顺序
先执行：
- `01-project-path.md`：串行。先把真实项目路径、Token、费用展示闭环做出来，否则“项目用量部分很好，要链接真实项目路径”的核心需求无法验收。

再执行：
- `02-request-log.md`：并行。可在 `01` 完成后与 `03` 并行；如果为了节省上下文成本，可和 `01` 共用同一个前端上下文，按 `01 -> 02` 顺序执行。
- `03-cost-billing.md`：并行。与 `02` 文件边界基本分离，建议单独上下文执行，避免和前端展示修复互相污染。

最后执行：
- `04-qa-feishu.md`：串行。必须等 `01`、`02`、`03` 合并到同一工作区后再执行，建议使用全新 QA 上下文，不要复用实现工单上下文。

## 上下文分配
- 共用上下文合适：`01-project-path.md` + `02-request-log.md`。二者都偏前端展示和测试修复，共用上下文能复用 dashboard/copy/test 认知，成本更低。
- 单独上下文合适：`03-cost-billing.md`。它跨 `src/lib/local-api.js`、`src/lib/api-billing.js`、`dashboard/src/hooks/use-cost-accumulation.js` 和支出页测试，风险边界独立。
- 单独新上下文必须：`04-qa-feishu.md`。最终验收不能由实现者自证，需要从干净视角复查文件、命令输出和飞书读回。

## 统一验收纪律
- 不接受“subagent 说完成”作为证据。
- 每个工单必须附命令输出、失败修复记录、复查结论。
- 修改用户可见文案必须走 `dashboard/src/content/copy.csv`。
- 修改 `src/` 或 `dashboard/` 后至少运行对应专项测试和 `npm --prefix dashboard run build`。

工单执行完成的最后增加一个审查环节，以对抗性审查的方式回写审查记录，如果出现问题就修复，修复执行完的环节依旧是对抗性审查，直到都完成了才能结束，并汇报给我工单的完成情况。
