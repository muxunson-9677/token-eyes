# 2.0 贝叶斯验收打回修复工单

## 中文简述
本目录用于修复当前 2.0 版本“页面能打开，但不能上线验收”的硬阻塞问题。依据来自 2026-06-30 的重新验收：请求日志分页已经基本可用，但真实项目路径、项目成本、发布 workflow、完整测试和独立审查证据仍不满足上线标准。

## 贝叶斯验收结论
假设 `H = 当前产品可以作为真实数据体验版上线并通过最终验收`。

| 证据组 | 当前证据 | 方向 | 似然比估计 |
|---|---|---:|---:|
| 先验 | 子代理声称 01/02/03 已完成，但上一轮审查记录存在自相矛盾 | 中性偏负 | `P(H)=35%` |
| 正向证据 | `validate:copy`、`validate:ui-hardcode`、`validate:guardrails`、dashboard typecheck/lint/build、cargo check、关键专项测试通过 | 正向 | `3.0` |
| 请求日志分页 | API page 1/page 2 各 10 条、总数 5000、总页数 500、时间戳不同 | 正向 | `1.8` |
| 项目真实路径 | 项目接口返回 5 个项目，但 `project_path_nonempty=0`、`path_kind=unknown:5` | 强负向 | `0.05` |
| 项目成本 | 项目接口返回 5 个项目，但 `project_nonzero_cost=0`；代码把数字返回值当对象读取 | 强负向 | `0.05` |
| 发布 workflow | `.github/workflows` 不存在，后端测试中 workflow 缺失引用 45 次 | 强负向 | `0.10` |
| 完整测试 | 后端失败项约 279 条；前端 `8 failed | 62 passed`，`16` 个失败测试，另有 worker 异常 | 强负向 | `0.15` |
| 审查可信度 | 旧审查记录把 `project_path` 全空解释为通过，并引用不存在截图 | 负向 | `0.30` |

按工程验收口径折算，当前后验概率低于 1%。结论：不能上线验收，只能作为内部预览继续修复。

## 工单目录
- `README.md`：总调度、贝叶斯验收表、派发矩阵。
- `01-data-contract-project-cost.md`：真实项目路径与项目成本数据契约修复。
- `02-release-gates-full-tests.md`：发布 workflow、完整测试和发布门禁修复。
- `03-independent-acceptance.md`：独立对抗性验收、飞书读回和最终放行判断。

## 推荐派发矩阵
| 子代理 | 执行方式 | 发哪些文件 | 说明 |
|---|---|---|---|
| 主线修复子代理 | 串行 | `README.md` + `01-data-contract-project-cost.md` + `02-release-gates-full-tests.md` | `01` 和 `02` 有强依赖，建议同一个上下文串行执行，避免数据契约和测试门禁相互打架 |

## 独立审查派发口令
```text

```

## 共用规则
- 不得把子代理写死为任何具体模型或工具。
- 不得用 GitHub/Gitee URL 冒充本地真实项目路径。
- 不得把未定价成本显示成真实 `$0`。
- 不得把完整测试失败简单归类为“历史问题”，必须给出证据。
- 不得把旧批次飞书记录当成本轮 2.0 贝叶斯修复验收记录。
- 所有“通过”结论必须有当前工作区的新鲜命令证据。

工单执行完成的最后增加一个审查环节，以对抗性审查的方式回写审查记录，如果出现问题就修复，修复执行完的环节依旧是对抗性审查，直到都完成了才能结束，并汇报给我工单的完成情况
