# Token Eyes Windows 客户端外发验收总调度

## 任务目标

本目录用于把当前 Token Eyes Tauri Windows 客户端修复到“可以交给外部测试者安装验证”的状态。目标不是增加产品功能，而是关闭发布快照、自包含运行时、依赖安全、可信签名、干净机器安装和错误恢复方面的缺口。

本轮结论分为三档：

- `不可外发`：存在任一 P0/P1、硬门禁失败或必要证据缺失。
- `可外部安装验证`：本目录全部硬门禁通过，可发给受控外部测试者；不自动等于正式生产上线。
- `可正式上线`：除本目录通过外，还必须满足项目正式 release、真实用户反馈、证书/分发和维护策略要求；本轮不自行授予该结论。

## 贝叶斯验收表

### 计算规则

验收假设：`H = 当前 Token Eyes Windows 客户端可以作为受控外部体验版交给别人安装验证`。

```text
先验赔率 = P(H) / (1 - P(H))
后验赔率 = 先验赔率 × 每组相对独立证据的似然比
后验概率 = 后验赔率 / (1 + 后验赔率)
加权总后验 = Σ(维度后验 × 维度权重)
```

证据强度：

| 证据 | LR | 计入条件 |
|---|---:|---|
| 执行者口头汇报或“看起来正确” | 1 | 不更新概率 |
| 代码定位 + 针对性失败/通过测试 | 4 | 保存测试名、命令、退出码、关键输出 |
| 真实本地 API/进程边界集成测试 | 6 | 必须启动真实子进程或真实 HTTP 服务 |
| 安装包解包清单 + 哈希 + 签名验证 | 8 | 使用本轮新构建产物 |
| 无 Node/无源码干净 Windows 安装闭环 | 12 | 保存环境清单、截图、日志和端点证据 |
| 依赖安全扫描 + 泄漏负向探针 | 8 | npm/RustSec/密钥扫描均提供新鲜结果 |
| 全新上下文独立复跑通过 | 5 | 不得复用开发者的结论 |
| 直接反例、缺证、输出冲突 | 0.05 | 对应维度立即回退并修复 |

相同测试重复运行、同一安装包重复解包、同一日志换一种描述属于相关证据，只能计算一次。硬门禁失败优先于数值结果。

### 验收维度

| 编号 | 验收假设 | 当前先验 P(H) | 权重 | 硬门禁 | 最低后验 |
|---|---|---:|---:|---|---:|
| B1 | 发布分支、HEAD、任务文件和构建输入可复现 | 0.20 | 15% | 是 | 0.99 |
| B2 | 安装包自包含 Node、CLI、Dashboard 与运行依赖 | 0.01 | 20% | 是 | 0.99 |
| B3 | 本地 API 启停、同步、数据持久化和错误恢复真实可用 | 0.55 | 15% | 是 | 0.99 |
| B4 | 依赖、密钥、日志、构建产物不存在未关闭高危风险 | 0.25 | 15% | 是 | 0.99 |
| B5 | EXE/MSI/NSIS 身份、版本、签名和发布资产可信一致 | 0.05 | 10% | 是 | 0.99 |
| B6 | 无 Node/无源码干净 Windows 安装、重启、重装、卸载通过 | 0.05 | 15% | 是 | 0.99 |
| B7 | 用户可见故障、全量测试、构建和发布流水线无回归 | 0.40 | 10% | 是 | 0.95 |

最终通过条件：

- B1-B7 全部达到各自最低后验。
- 加权总后验不低于 0.97。
- 没有未关闭 P0/P1。
- `npm run ci:local`、Dashboard 全测/类型/lint、Rust 测试/格式、npm audit、cargo audit、Tauri build 全部满足对应工单口径。
- 真实 Authenticode 校验必须为 `Valid`；自签名不算外发证据。
- 至少一个无 Node、无源码、无预存 Token Tracker 服务的干净 Windows 环境完成安装闭环。
- 缺少证书或干净机器时，必须输出 `BLOCKED`，不得降格成“基本通过”。

## 工单目录

- `01-发布基线收敛.md`：关闭 F3-F5，建立可复现 HEAD。
- `02-Tauri自包含运行时.md`：关闭 F1、F2、F9，实现真正内置后端。
- `03-安全签名与发布门禁.md`：关闭 F6-F8、F10，收紧依赖、签名和 CI。
- `04-干净Windows安装验收.md`：合流 02/03，做真实安装、重启、重装、卸载和数据验证。
- `05-独立贝叶斯终审.md`：由全新上下文复验 B1-B7 并给最终结论。
- `review-records.md`：主线 01/04 和独立 05 的集中记录；并行的 02/03 先把完整审查记录回写各自工单，04 合流时再把其提交 SHA 和摘要追加到集中记录，避免并行修改同一文件。
- `派发口令.md`：可直接复制给各 subagent 的调度文本。

## 执行顺序

```text
先串行：01

后并行（必须独立分支/worktree）：
02 || 03

再串行：
04 -> 05
```

| 阶段 | 工单 | 上下文建议 | 前置条件 |
|---|---|---|---|
| 第一阶段 | 01 | 主线调度上下文 | 当前工作区 |
| 第二阶段 | 02 | 新建“运行时封装”上下文 | 01 的稳定基线提交 |
| 第二阶段 | 03 | 新建“安全发布”上下文 | 01 的稳定基线提交 |
| 第三阶段 | 04 | 主线集成上下文；可复用 01 的调度上下文 | 02/03 均已提交并合流 |
| 第四阶段 | 05 | 必须全新独立上下文 | 01-04 完成回写、提交和证据齐全 |

02 和 03 只允许在独立 worktree 并行，不能共享同一个脏工作区。02 不修改依赖锁文件和 release workflow；03 不修改 Tauri 运行时启动实现。发生文件冲突时停止并交由 04 合流，不允许互相覆盖。

## 所有工单统一执行约束

1. 开始前完整读取 `AGENTS.md`、`CLAUDE.md`、本 README 和对应工单。
2. 开始前记录 `git status --short --branch`、HEAD、分支、Node/Rust/npm/Windows 版本。
3. 不使用 `git reset --hard`、`git checkout --`、`git clean`，不删除或回退用户无关改动。
4. 不使用 `git add -A`；逐文件核对任务归属。
5. 先保留失败证据，再写失败测试或探针，再做最小修复，再运行针对性和全量验证。
6. 构建成功不等于安装成功；开发机运行不等于干净机器运行；fixture 不等于真实安装。
7. 不读取、记录、截图、提交或回显真实 API Key、Cookie、令牌、`.env` 值和用户提示词/消息正文。
8. 所有命令记录原命令、退出码、关键输出和证据路径；无法执行必须记为缺证。
9. 允许创建任务范围的本地提交；禁止未经用户明确授权 push、发布 Release 或把安装包发给第三方。
10. 所有报告使用当前轮新鲜证据，不得复制旧测试报告冒充本轮结果。

## 每份工单的强制闭环

每份 01-04 工单结束前必须执行以下循环：

```text
复现反例 -> 最小修复 -> 针对性验证 -> 全量验证
    -> 对抗性自审 -> 发现问题则回到“复现反例”
    -> 无问题后回写工单和 review-records.md -> 汇报
```

对抗性自审必须主动寻找至少三个反例，不能只复述通过项。任何一轮发现问题都必须保留原失败记录并追加修复记录。只有最后一轮没有新 P0/P1、没有硬门禁失败、没有缺失证据时才能结束该工单。

01、04、05 直接追加 `review-records.md`。并行执行的 02、03 将每轮完整记录追加在各自工单的“执行回写”之后，不直接修改集中记录；04 合流时将两者的提交 SHA、轮次、结论和证据路径追加到集中记录。这样 02/03 没有共享写文件。

05 的独立性更严格：05 发现问题后必须退回 01-04 对应上下文修复；修复完成后重新创建全新的 05 审查上下文。修复者或已经参与失败定位的 05 上下文不得直接签发最终通过。
