# 03 - 安全、签名与发布门禁

## 目标

清零当前可修复的生产依赖高危漏洞，为 Windows EXE/MSI/NSIS 接入可信 Authenticode 签名，并让 release workflow 在完整测试、安全扫描、内置运行时和签名任一不满足时停止上传。

对应反例：F6、F7、F8、F10。对应贝叶斯维度：B4、B5、B7。

## 前置条件

- 01 已完成并提供稳定基线提交 SHA。
- 本工单在独立分支/worktree 执行。
- 可以与 02 并行，但不得修改 Tauri 运行时启动代码或资源打包实现。
- 真正完成签名需要可用的代码签名证书和 CI secrets；缺失时必须如实 `BLOCKED`。

## 第一性原理执行规则

1. 漏洞扫描退出 1 就是不通过；不能用“可能不会走到该代码”代替依赖链和可利用性证明。
2. 签名文件存在不等于签名可信；必须验证证书链、摘要算法、时间戳和 `Status=Valid`。
3. 自签名证书只能做流程测试，不能作为给外部用户分发的通过证据。
4. CI 只有在失败时真正阻止上传才叫门禁；关键词测试和注释不算。
5. secret 不能出现在命令行回显、环境转储、日志、artifact、截图或工单。
6. workflow 产生的文件名必须与 README/发布链接一致，避免构建成功但用户下载 404。
7. 先保存当前 audit 和签名失败证据，再做最小依赖/流水线变更。

## 执行步骤

### 1. 保存失败基线和依赖链

- [ ] 运行根目录和 Dashboard `npm audit --omit=dev`，保存漏洞、版本、依赖链和修复建议。
- [ ] 运行 `cargo audit --file src-tauri/Cargo.lock`，保存漏洞和 warnings。
- [ ] 用 `npm explain ws`、`cargo tree --invert quick-xml@0.39.4 --target x86_64-pc-windows-msvc` 确认 Windows 依赖链。
- [ ] 对当前 EXE、MSI、NSIS 运行 `Get-AuthenticodeSignature`，保存 `NotSigned` 证据。
- [ ] 检查 workflow 当前是否在测试、安全扫描、签名或 runtime 清单失败后仍可能上传。

### 2. 最小升级并防回归

- [ ] 优先升级直接依赖或锁文件到官方修复范围，禁止用 `audit --force` 引入无关大版本。
- [ ] Dashboard 至少消除 `ws` high 和 `engine.io-client` 相关 moderate；运行其 SDK/认证/实时连接相关测试。
- [ ] Rust 至少消除 `quick-xml 0.39.4` 两个 high；确认 Windows runtime/build 两条依赖链均更新。
- [ ] 对 RustSec `unmaintained/unsound` warnings 逐项分类：Windows 运行时可达、仅非 Windows、仅构建期、等待上游；无证据不能简单 ignore。
- [ ] 如必须添加 audit ignore，只能按具体 advisory ID、给出到期日期和不可利用证据；P0/P1/high 不允许无期限忽略。

### 3. 签名流程

- [ ] 明确正式证书来源、主体、有效期、时间戳服务和 CI secret 名称；文档只记录名称，不记录值。
- [ ] 在打包前签名主 `token-eyes.exe`，确保安装包内嵌 EXE 已签名；在生成后分别签名 MSI 和 NSIS。
- [ ] 使用 SHA-256 摘要和可信时间戳；任何签名步骤失败时 workflow 立即退出。
- [ ] 上传前对三个产物运行 `Get-AuthenticodeSignature`，必须全部 `Valid`，Signer Subject 符合预期，且证书未过期。
- [ ] 产出 SHA256SUMS 文件；哈希在签名后计算。
- [ ] 不在 PR/非受信 fork 环境解密或暴露证书 secret。

### 4. release workflow 硬门禁

- [ ] 使用干净 checkout 和锁文件安装。
- [ ] 上传前运行 `npm run ci:local`、Dashboard 全测/类型/lint、Rust 测试/格式、npm production audit、cargo audit。
- [ ] 调用 02 提供的 runtime prepare/build 接口；不得自行复制另一套 EmbeddedServer 逻辑。
- [ ] 解包或检查 MSI/NSIS，验证 `node.exe`、`tracker.js`、runtime manifest、dashboard index 和许可证存在。
- [ ] 验证 package、Tauri、Cargo、macOS project、旧 Windows csproj 等项目要求的版本一致性。
- [ ] 只有全部门禁和签名通过后才能上传；任一失败时 release 保持 draft 或根本不创建公开资产。
- [ ] 资产名称与 README 下载链接一致；明确唯一推荐的 Windows 外发安装包，避免用户下载旧 0.1.0 或旧品牌文件。

### 5. 负向 workflow 测试

- [ ] 测试缺证书 secret 时 release job 失败且不上传。
- [ ] 测试签名状态非 Valid、runtime 文件缺失、audit 失败、版本漂移时不执行上传步骤。
- [ ] 测试 workflow 不会打印 secret 或把证书临时文件上传为 artifact。
- [ ] 测试上传 glob 只匹配当前版本产物，不能把目录中旧版本一并上传。

产物完成后：

```powershell
$ReleaseRoot = (Resolve-Path "src-tauri\target\release").Path
$Artifacts = @(
  (Join-Path $ReleaseRoot "token-eyes.exe"),
  (Get-ChildItem (Join-Path $ReleaseRoot "bundle\msi\*.msi") | Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName,
  (Get-ChildItem (Join-Path $ReleaseRoot "bundle\nsis\*-setup.exe") | Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName
)
$Artifacts | ForEach-Object {
  Get-AuthenticodeSignature $_ | Format-List Status,StatusMessage,SignerCertificate,TimeStamperCertificate
  Get-FileHash $_ -Algorithm SHA256
}
if ($Artifacts.Where({ (Get-AuthenticodeSignature $_).Status -ne 'Valid' }).Count -gt 0) {
  throw "One or more Windows artifacts are not validly signed"
}
```

## 验收标准

- 根目录生产依赖 audit 无 high/critical；Dashboard 生产依赖 audit 无 moderate/high/critical，或存在用户明确批准且有到期日的非高危例外。
- Cargo audit 无 vulnerability；warnings 已按 Windows 可达性逐项记录，不能隐藏 high。
- 三个 Windows 产物的 Authenticode 状态均为 `Valid`，证书主体和时间戳正确。
- workflow 在测试、安全、runtime 清单、版本、签名任一失败时不上传。
- README 资产名称和 workflow 实际输出一致，不指向旧 `TokenTracker-Setup.exe` 或 0.1.0 文件。
- secret scan 证明证书、密码、API Key 和 `.env` 未进入日志/artifact。
- 计算 B4/B5/B7 的本工单阶段后验，B5 必须明确等待 04 的真实安装和 05 的独立复验；不得把 workflow 文本测试、签名命令和签名结果重复计为多组证据。

## 禁止事项

- 禁止用自签名结果宣称可外发。
- 禁止把证书 base64、密码、PFX 内容或真实 secret 写入工单、日志、命令历史或仓库。
- 禁止 `npm audit fix --force` 后不做回归。
- 禁止对 high vulnerability 加永久 ignore。
- 禁止只测试 workflow 文本包含某个字符串而不证明失败会阻止上传。
- 禁止在本工单复制一套与 02 不同的 runtime bundler。
- 禁止未经用户明确授权执行 push、创建/发布 Release 或向第三方分发安装包。

## 对抗性审查闭环

实现者至少主动攻击：

1. 删除一个 runtime 关键文件，workflow 是否仍上传。
2. 使用错误/过期证书或篡改签名后文件，签名门禁是否失败。
3. 构建目录同时放置 0.1.0 和当前版本，上传 glob 是否误传旧包。
4. 让 audit 返回 1，workflow 是否因 PowerShell 管道或错误处理仍继续。
5. 搜索 workflow 日志和 artifact 清单，确认没有 PFX、密码、密钥和 `.env`。

本工单与 02 并行，因此每轮完整记录追加在本文件“执行回写”之后，不直接修改集中 `review-records.md`。04 合流时再把本工单摘要写入集中记录。如果正式证书不可用，本工单可以完成依赖和 workflow 代码，但最终状态必须为 `BLOCKED`，B5 不得达标。
