# 01 - 发布基线收敛

## 目标

把当前混合了多轮任务改动的工作区收敛成可解释、可提交、可从干净检出重复构建的发布基线。此工单不实现自包含运行时、不接入签名，只解决文件归属、必要运行时文件入库、当前 CI/格式门禁和 HEAD 可复现问题。

对应反例：F3、F4、F5。对应贝叶斯维度：B1、B7。

## 第一性原理执行规则

1. 发布物只能来自版本控制中的确定输入；只存在于某台开发机工作区的文件等于不存在。
2. “当前工作区能构建”不能证明 HEAD 能构建；必须验证干净检出。
3. 未跟踪文件不能按“看起来像临时文件”批量删除，必须逐项判断归属。
4. 每一条纳入提交的变更都必须能追溯到已完成需求或本工单门禁修复；不顺手重构。
5. 先记录失败状态，再修复；禁止为了得到干净 status 而回退用户改动。
6. CI 硬门禁退出 1 就是不通过，不能以测试主体通过为理由忽略。

## 执行步骤

### 1. 冻结并分类工作区

- [ ] 保存 `git status --short --branch`、`git diff --stat`、修改文件列表和未跟踪文件列表到本工单回写，不创建新的根目录日志垃圾。
- [ ] 建立四类清单：`必须进入 HEAD`、`已完成但需用户确认`、`生成物/临时证据`、`归属不明不得处理`。
- [ ] 对每个生产代码引用的相对文件执行存在性与跟踪状态检查；至少覆盖两个已知未跟踪运行时文件。
- [ ] 检查 `.env`、密钥、截图、构建产物、`target/`、`dashboard/dist/` 不进入提交。

失败标准：无法解释的生产代码修改或运行时依赖仍留在 `??` 状态时不得继续宣称基线完成。

### 2. 先复现门禁失败

- [ ] 运行 `npm run validate:ui-hardcode` 并保存原始退出码和新增 raw text 位置。
- [ ] 运行 `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check` 并保存格式差异。
- [ ] 用 `git ls-files` 证明两个运行时文件修复前未进入 HEAD。
- [ ] 运行能引用 `provider-api-presets.js` 和 `glm.catalog.json` 的针对性测试，证明工作区依赖它们。

### 3. 最小收敛

- [ ] 把已确认属于当前产品的运行时文件和对应测试逐文件纳入任务提交。
- [ ] 将新增用户可见文本接入 `copy.csv`，修复 hardcode validator；禁止简单提高 rawText 基线掩盖问题。
- [ ] 对 Rust 任务文件运行 `cargo fmt`，只接受机械格式变化；审查没有语义改动。
- [ ] 对归属不明文件不删除、不提交，在回写中列出并说明为什么不影响本次发布输入。
- [ ] 形成一个或多个范围清晰的本地提交；提交信息使用英文 Conventional Commit。

### 4. 干净检出复现

- [ ] 从最终提交创建独立临时 worktree 或等价干净检出，不能继续使用原脏工作区作为证据。
- [ ] 在干净检出运行 `npm ci` 和 `npm ci --prefix dashboard`。
- [ ] 运行本工单必跑命令；不得从原工作区复制 `node_modules`、`dashboard/dist`、`target` 或未跟踪源码。
- [ ] 记录干净检出的 HEAD、命令、退出码和产物版本。

## 验收标准

- 两个已知运行时文件及其调用方、必要测试全部进入 HEAD。
- 没有生产代码引用只存在于未跟踪文件中的模块、JSON 或资源。
- `npm run ci:local`、Dashboard 全测/类型/lint、Rust 测试/格式全部退出 0。
- 干净检出不借用原工作区文件即可通过规定门禁。
- 任务相关 `git status` 干净；无关用户文件如仍存在，已列明且未被删除/提交/隐藏。
- 没有密钥、`.env`、日志、截图、构建产物进入提交。
- 计算 B1/B7 的本工单阶段后验并列出独立证据组，不为了达到阈值重复计算相关测试；最终 0.99/0.95 门槛由 05 加入独立复验后判定。

## 禁止事项

- 禁止 `git add -A`、`git clean`、`git reset --hard`、批量删除未跟踪文件。
- 禁止为了干净 status 回退用户已有修改。
- 禁止把旧 0.1.0 或新构建二进制提交进源码仓库。
- 禁止把 02/03 的工作提前塞入本工单。
- 禁止在没有干净检出证据时声明可复现。
- 禁止未经用户明确授权执行 push、创建/发布 Release 或向第三方分发安装包。

## 对抗性审查闭环

实现者至少主动攻击以下反例：

1. 在原工作区删除/临时移走两个未跟踪运行时文件后，构建是否暴露隐性依赖。
2. 干净检出是否因为缺文件、旧 dist、旧 target 或本机缓存而与原工作区不同。
3. 是否有宽泛 `.gitignore` 把本应提交的生产文件隐藏。
4. UI hardcode 是否通过“提高基线”而非接入 copy 注册表被掩盖。
5. Rust 格式是否只在开发机通过而干净检出失败。

每轮结果追加到 `review-records.md`。发现问题后保留失败记录，修复并开启下一轮对抗性审查，直到本工单无新 P0/P1、全部门禁通过才可结束。
