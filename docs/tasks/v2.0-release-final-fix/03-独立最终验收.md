# 03 - 独立最终验收

## 中文简述

本工单由全新上下文独立执行，不参与 01/02 的自证。它重新验证真实 API、真实浏览器页面、完整测试、macOS 与 Windows/Tauri 发布链路、Git 可复现性和飞书读回，只有全部硬门禁通过才能判定上线。

## 前置条件

- 01 和 02 均提交了完成报告。
- 主线提供代码状态、提交 SHA、测试日志、API 摘要、浏览器证据和飞书记录 ID。
- 主线停止修改验收范围文件，避免验收过程中基线漂移。

## 第一性原理执行规则

1. 验收者的职责是尝试推翻“可以上线”假设，而不是证明主线报告正确。
2. 所有证据必须来自当前提交和当前工作区的新鲜复跑，旧日志只能作为线索。
3. 完整测试、真实 UI、发布产物、Git 可复现性和数据真实性是硬门禁；任一失败都不能被贝叶斯分数抵消。
4. 构建通过不等于页面通过，页面通过不等于 workflow 可发布，局部测试通过不等于完整测试通过。
5. 发现问题必须记录可复现步骤、期望、实际和证据，再修复或打回；修复后重新从对应门禁开始。
6. 飞书状态必须晚于工程证据，不能用飞书“已完成”反向证明代码完成。

## 硬门禁

| 编号 | 验收项 | 不通过条件 |
|---|---|---|
| A1 | 项目真实数据 UI | 实际页面不显示路径/未检测提示、项目成本或远程仓库 |
| A2 | 项目 API 契约 | 路径冒充、缺少状态、成本语义失真或路径枚举不一致 |
| A3 | 请求日志 | 不是每页 10 条、页码不可跳转、两页数据相同或总数错误 |
| A4 | 成本累积 | API 计费、订阅成本、Token 套餐语义混淆或未连接冒充已同步 |
| A5 | 环境检测 | 设置页按钮缺失、检测状态错误或 Windows/WSL 判断失真 |
| A6 | 浏览器质量 | 核心路径报错、横向溢出、控制台存在未解释错误 |
| A7 | 完整测试 | 后端或前端完整测试非零退出码，或存在 unhandled/worker 错误 |
| A8 | 发布链路 | macOS DMG 或 Windows/Tauri workflow 路径、命令、产物不可信 |
| A9 | Git 可复现 | 干净检出缺文件、依赖未跟踪源码或无法复现构建 |
| A10 | 飞书读回 | 状态与证据不一致、未读回、提前标记 03 通过或泄露敏感信息 |
| A11 | 审查记录 | 只复述主线结论，没有独立命令和运行时证据 |

## 执行步骤

### 1. 建立独立基线

- [ ] 使用全新上下文和独立 worktree/干净检出。
- [ ] 记录分支、提交 SHA、`git status --short`、Node/Rust/npm 版本。
- [ ] 核对 01/02 范围内发布关键文件均被 Git 跟踪。
- [ ] 不读取旧“通过”结论作为新鲜证据。

### 2. 完整静态与测试门禁

- [ ] 运行 `git diff --check` 和所有校验命令。
- [ ] 运行 dashboard typecheck、lint、build。
- [ ] 运行 cargo check。
- [ ] 运行完整 `npm test`，记录总数、通过、失败、skip、退出码。

- [ ] 任何失败立即判定 A7 不通过，禁止继续写“有条件上线”。

### 3. 发布 workflow 对抗检查

- [ ] 验证 workflow display name、输入版本和 `vX.Y.Z` 标签一致。
- [ ] 验证 draft release、macOS 与 Windows 并行、全部成功后 publish。

- [ ] 运行 workflow 测试并人工核对测试是否覆盖真实命令。
- [ ] 如具备安全条件，使用非发布 dry-run 或 CI 验证；没有实际 CI 证据时必须明确剩余风险。

### 4. 真实 API 验收

启动：

```powershell

```

检查：

```text
/functions/tokentracker-project-usage-summary

/functions/tokentracker-request-usage-records?page=2&pageSize=10&limit=5000
/functions/tokentracker-api-billing-accounts
/functions/tokentracker-usage-summary
```

- [ ] 记录项目总数、路径非空数量、路径类型和状态分布。
- [ ] 记录成本大于 0 数量、定价覆盖率和至少 3 条脱敏项目样例。
- [ ] 验证远程 URL 不出现在本地路径字段。
- [ ] 记录两页请求日志的稳定 ID/时间戳、每页数量、总数和总页数。
- [ ] 验证未连接 API 计费账户的成本保持空值，不显示成已同步账单。

### 5. 真实浏览器 E2E

- [ ] `/dashboard`：打开项目用量，验证真实路径或未检测提示、远程仓库、Token、成本和定价状态。
- [ ] `/spend` 使用统计：验证趋势、Provider、模型、请求日志 10 条和页码跳转。
- [ ] `/spend` 成本累积：验证 Token 套餐、API 计费和订阅记录。
- [ ] `/settings`：逐个点击 Agent 环境检测，验证 Windows/WSL/未检测状态。
- [ ] 在桌面宽度和至少一个窄窗口宽度检查无横向溢出。
- [ ] 记录截图路径、关键 DOM 摘要、控制台错误和失败网络请求。
- [ ] 不得用旧截图或 mock 页面替代真实本地数据页面。

### 6. 飞书读回

- [ ] 读取 2.0-01、2.0-02、2.0-03 当前记录。
- [ ] 核对任务 ID、状态、阶段、更新时间和脱敏证据摘要。
- [ ] 03 在本工单最终通过前不得为“已完成/已验收”。
- [ ] 写入最终状态后再次读回。
- [ ] 报告不得输出 App Token、Table ID、App Secret、tenant token、Cookie 或 Authorization。

### 7. 贝叶斯复算与确定性放行

使用正确公式：

```text
先验赔率 O(H) = P(H) / (1 - P(H))
后验赔率 O(H|E) = O(H) × LR1 × LR2 × ... × LRn
后验概率 P(H|E) = O(H|E) / (1 + O(H|E))
```

- [ ] 不得把相关性强的证据重复相乘，例如“专项测试通过”和“同一专项 API 通过”不能被当作完全独立证据。
- [ ] 后验概率只作为风险摘要，不能覆盖 A1-A11 任一硬门禁。
- [ ] 正式上线建议要求 A1-A11 全部通过且后验概率不低于 95%。

## 最终判定

- `可上线`：A1-A11 全部通过，完整测试零失败，真实 API/UI 和 Git 可复现证据完整，飞书读回一致。
- `不可上线`：任一硬门禁失败。
- 不允许使用“有条件上线”“核心相关测试通过即可”“剩余问题发布后验证”等中间结论代替最终验收。

## 回写要求

在 `review-records.md` 增加“03 独立最终验收”，必须包含：

- 基线 SHA 和环境。
- A1-A11 逐项结论与证据。
- 完整命令及退出码。
- API、浏览器、workflow、Git 和飞书证据。
- 正确的贝叶斯计算过程。
- 问题、修复、复验轮次。
- 最终唯一结论：可上线或不可上线。

## 对抗性审查循环

首次审查发现问题时，不得结束工单。先在 `review-records.md` 记录问题和复现证据，再由主线或审查者完成最小修复；修复后重新执行受影响专项门禁，并再次执行两套完整测试、真实浏览器和 Git 可复现验证。重复直到 A1-A11 全部通过，或明确报告当前仍不可上线。

工单执行完成的最后增加一个审查环节，以对抗性审查的方式回写审查记录，如果出现问题就修复，修复执行完的环节依旧是对抗性审查，直到都完成了才能结束，并汇报给我工单的完成情况
