# 06 - 订阅记录必填契约修复

## 中文简述

本工单继续复用上一轮 `02-前端交互与订阅契约修复.md` 的上下文。当前独立验收发现：新增订阅记录时，如果请求缺少 `currency`、`billing_cycle`、`start_date`，后端仍返回 `200`，并静默默认成 `USD`、`monthly`、当天日期。这会让成本累积数据失真，不符合“用户输入什么就保存什么，缺必填字段必须明确报错”的契约。

## 第一性原理执行规则

- 成本数据的第一原则是可信，不是“尽量保存成功”。
- 订阅金额、币种、周期、开始日期是成本记录的核心字段；缺失时不能推断。
- 后端契约必须强于前端表单；即使 UI 正常，直接调用 API 的非法请求也必须被拒绝。
- 先用测试复现静默默认补齐，再做最小修复。
- 不允许用默认值掩盖用户输入错误，不允许把未知字段保存成看似合理的成本。

## 贝叶斯验收缺口

| 项目 | 修复前状态 | 新反例 | 影响 | 目标后验 |
|---|---:|---|---|---:|
| B6 端到端成本闭环 | 曾宣称达标 | 缺必填字段仍 200 并默认补齐 | 成本累积不可信 | >= 0.95 |

## 必须实现

1. 后端 create 场景必填校验。
   - `source` 必填。
   - `plan_label` 必填。
   - `amount` 必须是正数。
   - `currency` 必填且只能是 `USD` 或 `CNY`。
   - `billing_cycle` 必填且只能是 `monthly`、`yearly`、`one_time`。
   - `start_date` 必填且必须是有效 `YYYY-MM-DD`。

2. 后端 update 场景契约清晰。
   - 如果 update 是全量更新，则同 create 一样全部必填。
   - 如果现有代码语义是局部更新，必须在工单回写中说明，并确保传入空字符串/null 不会静默改写为默认值。
   - 不允许把非法或缺失字段默认成 USD/monthly/today。

3. normalize 只做格式标准化，不做核心字段推断。
   - 可以接受大小写标准化：`usd` -> `USD`，`ONE_TIME` -> `one_time`。
   - 不能接受语义改写：缺失 currency -> USD，缺失 cycle -> monthly，缺失 start_date -> today。

4. 错误码稳定。
   - 缺字段使用明确错误码，例如 `missing_required_field`。
   - 非法字段继续使用已有 `invalid_currency`、`invalid_billing_cycle`、`invalid_start_date` 或等价错误码。

### 执行摘要

修复订阅记录缺少 `currency`、`billing_cycle`、`start_date` 时仍被后端静默默认补齐为 `USD`/`monthly`/当天日期的问题。后端 `create` 场景现在强制校验全部 6 个必填字段（`source`、`plan_label`、`amount`、`currency`、`billing_cycle`、`start_date`），缺失/空值返回 400 + `missing_required_field` 错误码 + `field` 属性；非法值返回 400 + `invalid_currency`/`invalid_billing_cycle`/`invalid_start_date`/`invalid_amount`。`normalizeSpendRecord` 只做大小写/trim 格式标准化，不再语义推断缺失字段。UI 通过 `buildErrorFromResponse` 显示后端具体错误信息，不假装保存成功。

### 失败反例

复现命令：使用真实 local API handler + 临时目录发送缺必填字段的 POST 请求。

修复前实际结果（POST `{ source:"codex", plan_label:"Missing", amount:1 }`，缺少 currency/billing_cycle/start_date）：

```json
{
  "statusCode": 200,
  "body": {
    "ok": true,
    "record": {
      "amount": 1,
      "currency": "USD",
      "billing_cycle": "monthly",
      "start_date": "2026-07-03"
    }
  }
}
```

根因：`validateSpendRecordContract()` 只校验"已存在"的字段，允许缺失字段通过；`normalizeSpendRecord()` 对缺失字段默认补齐（`?? "USD"`、`?? "monthly"`、`isValidDate ? date : today`）。

修复前测试复现：新增 21 个后端测试，其中 15 个在修复前失败（证明反例成立）。

### 修改文件

1. `src/lib/local-api.js`
   - `validateSpendRecordContract(input, { mode })`：完全重写。`mode="create"` 时 6 个字段全部必填；`mode="update"` 时允许缺失（局部更新）但拒绝空字符串/null。每个字段有独立错误码 + `field` 属性。
   - `normalizeSpendRecord(record, fallback)`：移除所有语义默认（`?? "USD"`、`?? "monthly"`、`isValidDate ? date : today`）。只做大小写标准化（`usd`→`USD`、`ONE_TIME`→`one_time`）和 trim。缺失字段诚实返回空字符串。
   - `createSpendRecord(body)`：调用 `validateSpendRecordContract(payload, { mode: "create" })`。
   - `updateSpendRecord(body)`：调用 `validateSpendRecordContract(payload, { mode: "update" })`；defense-in-depth amount guard 补齐 `error_code`/`field`。
   - POST/PUT spend-records 错误响应：surface `error_code` 和 `field` 属性到响应体。

2. `dashboard/src/lib/api.ts`

   - `fetchLocalJson` 两处 `!response.ok` 块改用 `buildErrorFromResponse`，使 UI 能显示后端具体错误信息（如 "Missing required field: currency"）而非泛化的 "Request failed with HTTP 400"。

3. `test/spend-records-api.test.js`
   - 新增 21 个 06 契约测试（覆盖缺失/空字符串/null/非法值/合法值/大小写标准化/局部更新）。

4. `dashboard/src/pages/SpendPage.test.jsx`

### 剩余风险

1. **旧存储记录的读取路径**：`readSpendRecords` 调用 `normalizeSpendRecord`，旧记录如果存储时就没有 start_date（极少数手动编辑或更早版本创建的记录），现在会诚实返回空字符串而非 today。`computeSubscriptionCostForRange` 中 `new Date("T00:00:00Z")` 产生 Invalid Date，该记录不参与任何月份的成本计算。这是更诚实的行为，但可能导致旧损坏记录的成本汇总略有变化。正常用户记录不受影响（旧 normalize 在存储前已补齐默认值，存储的记录包含有效 start_date）。

2. **`fetchLocalJson` 改动范围**：`buildErrorFromResponse` 影响所有使用 `fetchLocalJson` 的端点（不仅是 spend-records）。改动是向后兼容的（`err.message` 从泛化变为具体，`err.status` 不变，新增属性是附加的）。全量回归 636 个前端测试通过，无破坏。

3. **UI 表单不预校验**：表单允许用户提交空 amount（`Number("") || 0` = 0），后端拒绝 0 并返回 `invalid_amount`。这符合"后端契约必须强于前端表单"原则，但用户体验可在未来增加前端预校验。
