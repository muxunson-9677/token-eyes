# Token Eyes 当前实现状态报告

日期：2026-06-18

## 结论先说

当前仓库已经可以启动，并且 `pnpm tauri dev` 能成功进入桌面应用启动流程，但它还不是计划里定义的“最小 MVP”。

更准确地说，当前实现是一个“CC Switch 既有产品壳子 + 部分新功能/新数据源准备 + 启动链路修正”的状态，而不是一个围绕 Hermes 数据链路、订阅费输入、费用汇总图表三件事收敛出来的阉割版最小 MVP。

当前本地开发端口已经改为 `3030`，因为原先的 `3000` 被你机器上已有的 Hermes workspace 占用。

## 和开发计划的对应关系

计划文档的 MVP 核心目标是：
- Hermes 用量统计
- Hermes 数据源路径手动输入
- 手动订阅费 CRUD
- `cost_ledger` 简化汇总
- 前端展示三个主要块：用量列表、花销图表、订阅费表单

但当前仓库实际可见状态是：
- 仍保留完整的 CC Switch 主壳和大量既有页面
- 仍有 Claude / Codex / Gemini / OpenCode / OpenClaw / Hermes 等多应用切换框架
- 当前主页主要还是“provider 管理”视图，不是计划里那种围绕 Hermes/MVP 的单页收敛界面
- 计划里明确说“本轮不做”的 OpenClaw、自动路径探测、复杂花销公式、UI 打磨等，仓库里依然存在很多相关旧能力或占位入口

所以从执行结果看，当前更像“在现有大产品上做一个局部适配”，而不是“只做计划里写的最小 MVP 核心面板”。

从现有截图看，主界面仍是 CC Switch 的主产品布局，顶部包含：

## 风险与偏差

### 1. 这个仓库不是“最小 MVP 收口版”

如果你要拿去给领导看，必须明确：
- 它现在能跑
- 但它不是计划书里定义的最小展示面

### 2. 端口是本机状态，不是产品设计

`3030` 只是为了避开本机已有 Hermes workspace 的占用。

也就是说：
- 这个端口不是产品的一部分
- 它只是这台机器上当前能跑通开发服务的临时配置

### 3. 目前界面信息量过大

对外沟通时，当前界面会显得：
- 功能很多
- 目标不聚焦
- 和“最小 MVP”叙事不一致

这也是你现在感觉“整个就是一个阉割版的 cc switch”的原因。

## 给领导沟通时的建议表述

你可以这么说：

> 当前仓库已经具备可运行的桌面壳和用量/配置能力，但它仍然保留了 CC Switch 的完整产品框架，不是严格按两天计划收敛出来的最小 Hermes MVP。现在更像是“可运行的基础版本”，而不是“只聚焦 Hermes 统计、订阅费和花费汇总的最终展示版”。如果要继续按计划推进，需要再做一次产品收口，删掉非 MVP 入口，把首页改成只服务 Hermes 的最小工作台。

## 如果要继续往计划收口，下一步应该做什么

建议的下一步不是继续加功能，而是先收口：
- 首页只保留 Hermes 相关内容
- 统计页只保留计划里的三块核心信息
- 暂时隐藏或移除与本轮 MVP 无关的 provider 管理入口
- 把 `3000` 这种历史端口配置统一清理成明确的本机开发说明

## 当前状态一句话总结

当前项目是“能启动、能看见、但未按计划收口”的 CC Switch 全量壳子，不是计划里那种严格最小化的 Hermes MVP。
