# Token Eyes V2.1 — 快速验证版MVP方案

> 这份不是要重新做一套东西,是从`token-eyes-full-plan-for-codex.md`里抽出最小子集,目的只有一个:**尽快跑出一个能看的版本,让人类负责人确认"这就是我要的方向",再决定要不要把H的自动刷新、完整花销周期逻辑等更复杂的部分铺开做**。基座、数据模型、飞书集成这些不变,跟全量方案保持同一套地基,区别只在于"这一轮先做哪些任务,哪些明确往后推"。

## MVP要看到什么(验收标准)

打开应用,看到一个Dashboard,**同屏能看到Win本机Codex + WSL内Claude Code/Hermes Agent三者的真实token用量数据**(这是最核心的、必须验证的部分,因为跨环境统一展示是本项目唯一的差异化亮点),用量带成本(哪怕汇率是个写死的占位数字)、带缓存命中率卡片;再有一个简化版花销页,能手动加一条订阅记录并看到汇总数字;设置页能看到路径覆盖的输入框。Token Plan的"自动刷新"这次先不做,放一个手动录入的占位表单即可,功能完整版留到确认方向之后再做。

## 这一轮包含的任务(对应全量方案里的编号)

- 0、0a:仓库初始化、飞书表初始化(跟全量方案一样,不简化,因为这是流程基础设施,不做反而后面更乱)
- 1:验证三个Agent解析器真实可用(核心,必须验证,这是整个产品成立的前提)
- 4、5:跨环境路径覆盖功能(核心差异化亮点,本轮必须做出来)
- 6、7:自定义计费规则——**简化版**:不用做到每个model都能单独配置,先支持给每个Agent设一个默认单价就行,够展示出"有成本数字"即可
- 8、9:USD/CNY换算——**简化版**:写死一个汇率常量,不用做成可配置项,先能看到人民币数字就行
- 10:缓存命中率卡片(工作量小,直接做完整版)
- 14、15:花销模块——**简化版**:只做"新增一条订阅记录+列表展示+简单求和",不用区分月付/年付的周期换算逻辑,先能加记录、看到一个总数就行
- 16:隐藏Skills Manager/Leaderboard(工作量小,顺手做掉)
- 17、18:跑一次基本联调,Codex审核合并

## 这一轮明确不做,推到方向确认之后(全量方案里的编号)

- 2、3:Hermes细分DeepSeek/小米计费线——除非任务1验证后发现这个问题严重到完全没法展示成本,否则先不管,展示成"Hermes"一个笼统来源也能验证方向
- 11、12、13:**Token Plan自动刷新整套机制**(刷新间隔配置、官方API/Cookie抓取判定逻辑、失败报错处理)——这是全量方案里工作量和风险都偏高的一块,本轮只放一个"手动填套餐名/额度/到期时间"的占位表单,占住UI位置,验证布局合不合适就够了,真正的自动刷新等方向确认后再开发

## 给Codex的提醒

写工单时在每张工单标题里加上"[MVP]"前缀,方便和后续全量版的工单区分;MVP阶段产出的"简化版"代码不是最终版本,后续做全量版时这些工单可能需要重新设计接口(比如计费规则从"每Agent一个单价"扩展到"每Agent+model一个单价"),不算是返工浪费,提前告诉 Claude Code 这部分以后可能要改,写代码时不用过度设计,做到能跑通就行,不用预留太多扩展性。
