审查日期：2026-07-26  
审查对象：当前工作区快照（分支 `codex/token-eyes-fixes`，HEAD `d4b7bee4`，包含尚未提交的现有改动）

## 一、结论

当前项目的核心 Token 采集和桌面壳并非整体不可用：Dashboard 可以完成生产构建，Tauri 有效库单测 143/143 通过，依赖漏洞审计为 0，架构/文案校验也通过。

但当前快照不适合直接发布，主要原因是：

1. 本地 API 的只读数据可被任意网页跨域读取，和“本地隐私优先”承诺冲突。
2. 完整 CI、前端测试、TypeScript、ESLint、完整 Rust 测试均未通过。
3. GitHub 发布工作流在当前分支缺失，约 50 个发布契约测试因此失败。
4. Token 套餐的 Kimi 官方账号保存分支存在不可达代码，可能丢失账号绑定。
5. Windows 测试可能读取真实用户凭据和真实 Token 数据，导致测试污染、真实接口调用及日志泄露。
6. Trae 接入后，Node、Dashboard、macOS 三端注册表没有同步完成。
7. README、历史 CC Switch 代码和当前实际产品边界已经明显错位。

建议先完成 P1，再处理 P2。P1 未清零前不建议制作正式安装包。

## 三、P1：发布前必须解决

### P1-01 任意网页可跨域读取本机 Token 使用数据

**位置**

- `src/lib/local-api.js:1576`
- `src/lib/local-api.js:3956`
- `src/commands/serve.js:97`

**现象**

本地服务只绑定 `127.0.0.1`，但所有 JSON 响应统一返回：

```http
Access-Control-Allow-Origin: *
```

大量 Token、请求、模型、项目、成本、套餐和本地设置读取接口不要求本地认证。用户只要正在运行 Token Eyes，浏览器中打开的任意恶意网站就可以直接请求 `http://127.0.0.1:7680/functions/...` 并读取响应。

写接口已有本地 token 和 Origin 校验，因此主要风险不是远程修改，而是本地隐私数据被网页窃取。

**影响**

- 泄露 Token 使用时间、模型、Agent、项目归属、成本和请求明细。
- 与 README 的“Only token counts and timestamps never leave your machine”承诺不一致。
- 浏览器恶意页面不需要攻破主机，只需要本地服务正在运行。

**针对性修复**

1. 不再对普通 API 返回 `Access-Control-Allow-Origin: *`。
2. 只允许当前 Dashboard 的 loopback Origin、`tauri://localhost`、`http(s)://tauri.localhost`。
3. `/api/local-auth` 也应按允许 Origin 动态回显，并加 `Vary: Origin`。
4. 对敏感 GET 接口同样要求本地 auth token；至少先保护请求明细、项目、设置、套餐、Provider 账户和余额。
5. 增加恶意 Origin 回归测试：`Origin: https://evil.example` 的预检、握手、GET、POST 都必须失败。

**验收标准**

- 恶意网页 Origin 无法读取任何本地使用数据。
- CLI/curl 无 Origin 的本机调用仍可按设计工作。
- Dashboard 开发端口、Tauri WebView、正式本地端口均可正常访问。

### P1-02 显式端口会杀死占用端口的任意进程

**位置**

- `src/commands/serve.js:206-244`

**现象**

用户指定 `--port` 或 `PORT` 后，`ensurePortFree()` 使用 `lsof` 查到占用 PID，直接发送 `SIGTERM`，3 秒后仍在则发送 `SIGKILL`。代码没有确认目标 PID 是否属于 TokenTracker。

**影响**

如果端口被数据库、开发服务器或其他软件占用，TokenTracker 可能直接终止无关进程并造成未保存数据丢失。

**针对性修复**

- 首选：显式端口被占用时直接报错，不自动杀进程。
- 如必须支持“清理旧实例”，只能终止由 TokenTracker 自己写入并验证过的 PID 文件，且同时校验进程命令行、启动时间和监听端口。
- 删除通用 `SIGKILL` 兜底，或将其限制在已验证的 TokenTracker 子进程。

**验收标准**

- 用其他进程占用测试端口，启动 TokenTracker 后该进程仍存活。
- 旧 TokenTracker 实例可以通过受控的 PID/健康检查机制复用或停止。

### P1-06 测试会读取真实用户凭据和真实 Token 数据

**位置**

- `src/lib/subscriptions.js:122-145`
- `src/lib/data-directories.js:45-62`
- `test/helpers/home-shim.cjs`
- `test/usage-limits.test.js`
- `test/usage-limits-singleflight.test.js`

**现象**

测试虽然传入临时 `home`，但没有隔离传给数据目录解析的 `env`。`listCodexHomeCandidates()` 默认回退到真实 `process.env`，因此真实 `CODEX_HOME`/AgentData 路径仍可进入搜索顺序。

实际测试中观察到：

- 使用了真实 Codex 账号 ID，而不是测试 fixture。
- 调用了真实账号对应的 quota URL 分支。
- 本地 API 测试读取了真实 `~/.tokentracker` relay cookie 和 queue。
- 失败输出打印了大量真实 Token 队列数据。

**影响**

- 测试不确定、跨机器不稳定。
- 可能触发真实供应商接口和限流。
- CI/终端日志可能泄露个人使用历史。
- “67 个失败”中一部分是环境污染，而不是业务断言本身。

**针对性修复**

1. 所有可测试的路径解析函数显式接收并透传 `home`、`env`、`platform`，禁止深层函数重新读取 `process.env`。
2. 测试统一使用全局 preload，而不是由部分测试文件手动 `require(home-shim)`。
3. 测试启动时清空或替换 `CODEX_HOME`、`CLAUDE_CONFIG_DIR`、`APPDATA`、`LOCALAPPDATA`、`USERPROFILE`、AgentData 相关变量。
4. 网络层默认 deny；只有传入 fake fetch 的测试才能发请求。
5. 失败快照不得打印完整 queue、cookie、账号 ID 或凭据路径。

**验收标准**

- 断网、空用户目录环境可运行全部 Node 测试。
- 测试日志不再出现真实用户目录、账号 ID、真实模型历史。
- `usage-limits` 两个文件单独和全套运行结果一致。

### P2-03 `visibleProviderIds` 未传时错误地变成空 sources

**位置**

- `dashboard/src/hooks/use-request-usage-records.ts:117-141`
- `dashboard/src/hooks/__tests__/use-request-usage-records.test.tsx`

**现象**

契约要求“不传 `visibleProviderIds` 表示查询全部”，当前实际请求却发送 `sources: []`。这和显式传空数组（表示用户隐藏全部 Provider）语义冲突。

- `undefined`：不施加 Provider 可见性过滤；
- `[]`：明确不查询，直接返回空；
- 非空数组：与其他过滤器求交集。
